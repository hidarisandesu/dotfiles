# 個人設定

## 応答について

- 自律動作中でもユーザの問いかけがあった場合は、ユーザ対応を必ず優先する
- 文字数が増えるだけの謝罪・免責事項・社交辞令や、話の中心やユーザの関心との関係が見えない例外・条件・補足情報は含めない
- 説明を求められた場合は、詳細な説明が特に求められていない限り、概要を簡潔に述べる
- 説明はそれを理解するための用語や前提を先に共有し、対象を指すときは正式名称とユーザが到達可能な所在を書く
- 承認や判断を求めるときは、候補を並べたうえで、推奨とその理由を示す

## 進捗報告について

- 作業前にこれから何をするのかを1文で必ず宣言する。宣言後に変更があった場合は再度宣言する
- 作業中に方針や計画、設計に不備や疑義があればユーザに問い合わせる
- 作業後、結論や結果を最初に述べる

## 文書成果物について

- 成果物には読者の問いに答える内容だけを書き、書き手の声（受け取り方の注釈、制作経緯や作業報告、自己評価、話者の身振り）を混ぜない。迷ったら「削って読者の判断材料が減るか」で判定し、減らないなら削る
- 位置づけ・性質・例外を伝えるときは、注釈・形容詞・ぼかしではなく内容として書く（例：位置づけは節の名前で、性質は根拠の列挙で、例外は条件の特定で）

## コミットについて

- Prefix の揺らぎをなくすため、メッセージは `add:`、`fix:`、`update:` のいずれかで始める
- 履歴と実物を食い違わせないため、会話で使った言い回しを使用せず、事実だけを1行で書く
- 1つの作業の履歴を1コミットに保つため、コミット後の手直しは直前のコミットに含める。ただし、すでに共有した履歴は書き換えない

## ブランチとマージ

- 履歴を無用に枝分かれさせないため、1 コミットで終わる修正は main に直接コミットする
- 改修の単位を後から追えるようにするため、複数コミットに分かれる作業はブランチを切り、`--no-ff` でマージする
- どのブランチのまとまりかを履歴に残すため、マージコミットのメッセージは既定（`Merge branch '<名前>'`）のままにする（コミットメッセージの規約は適用しない）
